wire_protocol.txt — Driver Station ⇄ Laptop Relay ⇄ Pi Client (v0.3)

Goal
  JSON application protocol transported over WebRTC DataChannels.

  The migration removes WebSocket/TCP as the rover application transport.
  The HTTP server is used only for WebRTC SDP signaling.

  WebRTC DataChannels use:
    SCTP over DTLS over UDP

  DataChannels:
    cmd        - unordered / unreliable
    telemetry  - unordered / unreliable
    control    - ordered / reliable
    heartbeat  - unordered / unreliable

Supports:
  - low-latency teleop commands (<= 20 Hz)
  - configurable telemetry stream (default 10 Hz)
  - e-stop
  - action queue (drive goals)
  - alerts
  - ownership/mux (teleop vs auton)
  - connection heartbeat / RTT

Transport / signaling
  HTTP signaling endpoint on laptop port 8765:

    Pi:
      POST /api/webrtc/pi/offer

    Browser:
      POST /api/webrtc/browser/offer

  Request body contains:
    { "sdp": "...", "sdp_type": "offer" }

  Response contains:
    { "ok": true, "sdp": "...", "sdp_type": "answer" }

  Once the PeerConnection is established, application messages MUST use the
  appropriate DataChannel. There is no WebSocket fallback.

Timing / Identity
  ts_ms  : sender wall-clock timestamp in milliseconds
  seq    : per-direction increasing sequence number where useful
  id     : request/transaction identifier used for matching responses

Units
  cmd.c*_lx : linear-x command, meters/second
  cmd.c*_az : angular-z command, radians/second
  imu.rpy   : roll/pitch/yaw, radians
  enc.*     : wheel speeds, revolutions/second
  bat.v     : volts
  bat.i     : amps
  net.*     : kbps, milliseconds

Behavior rules
  - cmd messages SHOULD be sent at <= 20 Hz.
  - cmd uses unordered/unreliable delivery. New commands supersede old commands.
  - telemetry uses unordered/unreliable delivery. Stale telemetry may be dropped.
  - control is ordered/reliable for state-changing commands.
  - heartbeat uses its own unordered/unreliable channel so heartbeat traffic
    cannot block e-stop or other control traffic.
  - mux determines who is allowed to command motion.
  - Pi command watchdog MUST stop teleop motion when valid cmd traffic is lost.
  - estop is a latch: once asserted, motion remains stopped until cleared.

# -----------------------------------------------------------------------------
# Browser/Laptop -> Pi
# -----------------------------------------------------------------------------

1) Heartbeat
  Channel: heartbeat
  Purpose: detect stale transport and measure RTT
{ "t":"hb", "id":421, "ts_ms":12345678 }

2) Teleop command
  Channel: cmd
  Purpose: current joystick command; old commands may be discarded
{ "t":"cmd", "seq":812, "ts_ms":12345680, "c1_lx":0.25, "c1_az":-0.30 }

3) Emergency stop
  Channel: control
  value=true  : latch e-stop ON
  value=false : clear e-stop
{ "t":"estop", "ts_ms":12345681, "value":true }

4) Set / reconfigure telemetry stream
  Channel: control
{ "t":"set", "telemetry_hz":10,
  "tlm_fields":["imu","enc","bat","net","mux","queue"] }

5) Mux / ownership request
  Channel: control
{ "t":"mux.request", "ts_ms":12345690, "mode":"teleop" }

6) Queue a drive action
  Channel: control
{ "t":"queue.drive", "id":"drive-17",
  "distance_m":1.0, "heading_deg":0,
  "max_speed_mps":0.4 }

7) Cancel current queue action
  Channel: control
{ "t":"queue.cancel", "ts_ms":12345700 }

# -----------------------------------------------------------------------------
# Pi -> Laptop/Browser
# -----------------------------------------------------------------------------

1) Hello / handshake
  Channel: control
{
  "t":"hello.ack",
  "ver":"0.3",
  "client":"pi",
  "caps":["telemetry","teleop","queue","estop","webrtc_datachannels"]
}

2) Heartbeat acknowledgement
  Channel: heartbeat
{ "t":"hb.ack", "id":421, "ts_ms":12345705 }

3) Mux state broadcast
  Channel: control
{ "t":"mux.state", "ts_ms":12345706,
  "mode":"teleop", "owner":"pi" }

4) Telemetry frame
  Channel: telemetry
  Pushed at telemetry_hz, default 10 Hz.

{
  "t":"tlm",
  "seq":9321,
  "ts_ms":12345710,

  "mux":"teleop",

  "imu":{"rpy":[0.02,0.01,1.57]},
  "enc":{"l_rps":1.22,"r_rps":1.19},
  "bat":{"v":11.9,"i":1.2},

  "net":{
    "ctl_kbps":8,
    "tlm_kbps":22,
    "vid_kbps":900,
    "rtt_ms":25
  },

  "cmd_echo":{
    "c1_lx":0.25,
    "c1_az":-0.30,
    "c2_lx":0.0,
    "c2_az":0.0
  }
}

5) Queue state
  Channel: control
{
  "t":"queue.state",
  "ts_ms":12345720,
  "active":{"id":"drive-17","progress":0.42,"remaining_m":1.10},
  "pending":[{"id":"drive-18"},{"id":"drive-19"}]
}

6) Queue result
  Channel: control
{
  "t":"queue.result",
  "ts_ms":12345740,
  "id":"drive-17",
  "success":true,
  "reason":"Done"
}

7) Alerts / warnings / errors
  Channel: control
{
  "t":"alert",
  "level":"warn",
  "msg":"IMU timeout 200 ms"
}

# -----------------------------------------------------------------------------
# Suggested defaults
# -----------------------------------------------------------------------------

  heartbeat_hz        = 5
  command_hz_max      = 20
  telemetry_hz       = 10
  command_watchdog_ms = 250

# -----------------------------------------------------------------------------
# Extensibility guidance
# -----------------------------------------------------------------------------

  - Add new message types with a namespace: nav.*, slam.*, arm.*
  - Keep existing keys stable.
  - Add new keys instead of renaming existing ones.
  - For compact/high-rate telemetry, add a new type such as tlm2.
